## 1. 本レポートの位置づけ

前回レポート (Trial 5) では、推論入力と推論の主体が実機と乖離していた。
本レポートではその 2 点を実機に合わせた上で再比較を行う。

### 実機との乖離（修正前）

| 項目 | 修正前 (Trial 5) | 実機 (start.py) |
|------|-----------------|----------------|
| 推論入力の最初2次元 | `needTP, needRTT`（アプリ要求品質） | `measured_tp, measured_rtt`（現在APの実測値） |
| 推論の主体 | 各端末が独立に自分のモデルで推論 | エッジサーバがグローバルモデルで全端末を一括推論 |
| 教師データの最初2列 | `needTP, needRTT` | `measured_tp, measured_rtt` |

### 修正内容

1. **推論入力** (`terminal.py`): `_TP_NEEDS[app_idx]` / `_RTT_NEEDS[app_idx]` → `ap_conditions[cur_ap]`（端末が現在接続中のAPで実測した TP/RTT）
2. **推論の主体** (`runner.py`): `SimTerminal.run_inference()` → `HFLRunner._edge_inference()`（グローバルモデルで一括推論。実機 `start.py` L1096-1117 の `_do_inference_snapshot()` に対応）
3. **教師データ** (`gen_3ap_training_data.py`): CSV の先頭2列を端末の現在AP実測 TP/RTT に変更

### 実機コードとの対応

```python
# 実機 start.py L1096-1106 (_do_inference_snapshot)
for tid in sorted(terminal_data.keys()):
    record = terminal_data[tid]

    _, probs = _forward(inp)                              # グローバルモデルで推論
```

### 3.3 seed=42 詳細分析

seed=42 は差が最も顕著なケース。挙動の違いを詳しく見る。

**6次元モデル — 全端末AP0集中の罠**:

```
R1: n_on_ap=[2,2,0]  → pred: 全員AP0  → R2: n_on_ap=[4,0,0]
R2: n_on_ap=[4,0,0]  → pred: 全員AP0  → R3: n_on_ap=[4,0,0]
...（R2〜R18まで全員AP0、17ラウンド連続）
R19: ようやくT2,T3がAP1へ  → n_on_ap=[2,2,0]
R20: T2,T3がAP0に戻る → n_on_ap=[4,0,0]
R21〜R30: 再び全員AP0に固定 (10ラウンド連続)
```

4台がAP0に集中 → M/M/1 で RTT 急騰:
- AP0 (mu=8, n=4): virtual_rtt = 1/(8-4)*1000 = **250ms** → sat(other) = 30/250 = **0.12**
- AP1 (mu=12, n=0): virtual_rtt = base 100ms → sat(other) = 30/100 = **0.30**

6次元モデルは AP1 が空いていることを知らないため、全員AP0に留まり続ける。

**15次元モデル — AP分散の維持**:

```
R1: n_on_ap=[2,2,0]  → T0,T1→AP0, T2,T3→AP1  → R2: n_on_ap=[2,2,0]
R2〜R30: 28ラウンド連続で n_on_ap=[2,2,0]、切替なし
```

15次元モデルは全APの TP/RTT/接続台数を見て「AP0に全員行くと混雑する」ことを認識 → T2,T3 を AP1 に留める:
- AP0 (n=2): RTT ≈ 170ms → sat(other) = 30/170 = **0.18**
- AP1 (n=2): RTT ≈ 100ms → sat(video) = 50/100 = **0.50**
- 平均 sat = (0.18×2 + 0.50×2)/4 = **0.34**（6次元の 0.16 の2倍以上）

実機忠実化しても **傾向は同一**: 精度は差なし、満足度は15次元が安定的に優位。

ただし、実機忠実化により以下の変化が生じた:

1. **入力が測定値になったことで、AP集中問題がより顕著に出現** — needTP/needRTT は全端末で固定値だったが、measured TP/RTT は接続APの混雑で変動するため、「全員同じAPにいると同じ劣化した入力を見る → 全員同じ予測をする → 集中が固定化する」という正のフィードバックループが発生しやすい
2. **エッジサーバ一括推論により、全端末が同一モデル（グローバルモデル）で予測** — 端末ローカルモデルの個体差が消え、同一入力 → 同一出力の傾向が強化

## 5. なぜ15次元モデルで満足度が向上するのか

### 根本的な理由

6次元モデルの入力 `[measured_tp, measured_rtt, one_hot(app)]` は **自分の現在APの状態しか見えない**。
15次元モデルの入力は加えて `[AP0_tp, AP0_rtt, AP0_n, AP1_tp, AP1_rtt, AP1_n, AP2_tp, AP2_rtt, AP2_n]` — **切り替え先APの品質を知った上で選べる**。

### 具体的メカニズム

```
6次元の挙動:
  入力: [自AP の TP=250, RTT=250ms, app=other]
  → 「RTTが高い、他のAPがいいかも」
  → でも他のAPの状態は不明 → 教師データの多数派（AP0: 50%）に引きずられる
  → 結果: 全員AP0 → 混雑 → 満足度0.12〜0.20

15次元の挙動:
  入力: [自AP の TP=250, RTT=250ms, app=other, AP0: TP=250/RTT=250/n=4, AP1: TP=200/RTT=100/n=0, ...]
  → 「AP0は4台で混雑、AP1は0台で空いている」
  → AP1の方がRTT低い → T2,T3をAP1に割当
  → 結果: n_on_ap=[2,2,0] → 分散 → 満足度0.31〜0.41
```

重要なのは **「精度が高いから満足度が高い」のではない** という点。
精度は同等（~62%）だが、15次元モデルは **切り替え先の状態を考慮した予測** ができるため、結果として混雑回避が実現し、満足度が向上する。

## 6. 結論

### 精度
6次元と15次元で統計的有意差なし（5シード平均: 62.3% vs 62.0%）。実機忠実化後も同一傾向。

### 満足度
15次元モデルが一貫して優位（+0.098, +20.7%）。特に6次元モデルが全端末AP0集中に陥るケースで差が顕著（seed 42, 123: +0.18）。

### 優位性の本質
AP状態特徴量は「分類精度の向上」には寄与しないが、**「切り替え先APの品質を知った上での判断」** を可能にし、不要な集中・振動を防ぐ。これは精度からは測定できない実運用上の利点である。

### 実機実験への示唆
- 15次元モデルを実機実験で使用することを推奨
- 特に端末数が多い環境（AP集中リスクが高い）で効果が大きいと予想
- 教師データは `[measured_tp, measured_rtt, appIdx, AP_states..., label]` 形式で生成すべき
