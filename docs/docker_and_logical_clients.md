# Docker・論理クライアント（研究メモ）

> **目的**: 会話で整理した「Docker 仮想端末と実 Android 端末の違い」「論理クライアントの定義」「教師データ配布時の含意」「TP/RTT の実数性」を、論文・計画書で参照できる形に固定する。  
> **関連**: `docs/experiment_scale_provisional.md`（台数・Docker あり/なしの暫定方針）、`docker/docker-compose.yml`（ルートの `compose.yaml` から include 可）、`terminal_client/main.py`

---

## 1. 本プロジェクトにおける Docker の位置づけ

Docker は次の **2 役**に分けて考える（`experiment_scale_provisional.md` と同じ整理）。

| 役割 | 内容 | 主な目的 |
|------|------|----------|
| **(A) サーバの再現環境** | セントラル・エッジ（および Redis 等）をコンテナで起動 | 査読・提出・スナップショット再現 |
| **(B) 仮想端末クライアント** | `terminal_client` などが HTTP でエッジに参加 | プロトコル検証、同時接続・負荷、**論理クライアント数**の増減 |

**主張の核は実機＋生データ／実リンクに置く**のが無難であり、(B) は **Android の代替**ではなく **補助実験・インフラ試験**として割り切る（暫定方針と一致）。

---

## 2. 論理クライアント（logical client）の定義

**論理クライアント**とは、階層連合学習のプロトコル上 **1 台のクライアントとして区別される ID を持ち**、所定の API に従ってローカル学習・モデル送受信・（必要なら）エッジへの参加を行うソフトウェア実体である。一方で、**実 Android 端末・無線インタフェース・OS 上の計測パイプライン・実際の AP 切替**といった物理的・リンク層の前提を **必ずしも備えない**。

**論文・計画書向けの短文（案）**  
本研究における論理クライアントは、連合学習のクライアント ID として集約に寄与するが、必ずしも実機・実リンク観測を伴わない参加者を指す。

**クライアント数の記載**では、「実機のみの N」と「プロトコル参加者数（論理クライアント含む）」を **別記**すると、実数／合成の主張と矛盾しない。

---

## 3. 実端末クライアントと論理クライアントの対照

| 観点 | 実端末（Android） | 論理クライアント（例: Docker `terminal_client`） |
|------|-------------------|--------------------------------------------------|
| **プロトコル** | エッジ／セントラルと HTTP 等で参加 | 同様に参加しうる |
| **学習実装** | Kotlin / PyTorch Android（`LocalTrainer` 等） | Python / PyTorch（別スタック）→ **勾配・重みの完全一致は期待しにくい** |
| **そのラウンドの TP/RTT** | 無線・OS 経由で実リンクに近い観測（設計依存） | **CSV の行・生成モデル・`virtual_congestion` API 等**。同じ瞬間の空気を測っていない |
| **AP 選択** | 実接続・ハンドオーバーと結びつきうる | 多くは **選択の報告**にとどまり、実リンクと一致しないことが多い |
| **環境** | バッテリー・熱・バックグラウンド制限 | サーバ CPU・常時オン。実機のドロップアウト・負荷は別問題 |

仮想端末の通信先の例は `terminal_client/main.py` 先頭コメント（`/send_to_device`、`/upload_biases`、`/api/v1/virtual_congestion/...` 等）を参照。

## 4. 教師データ（ラベル付き学習データ）を配布した場合

**配布した CSV を論理クライアントが読めば**、特徴量・ラベルの分布は **実機に近づけられる**（FedAvg で混ぜたときの **データ分布のズレは小さくなりうる**）。

ただし **論理クライアントが実端末と等価になるわけではない**。残る差は少なくとも次のとおり。

- **学習パス**: Kotlin Android と Python は同一実装ではない。
- **ライブ観測**: ファイル上の数値は「過去の記録の再生」であり、そのラウンドの **生きた電波の測定**ではない（CSV の出所が実測ログでも同様）。
- **AP の物理的意味**: 実ハンドオーバーとの対応は論理側では弱い。

**実装上のメモ（現状）**: `terminal_client/main.py` は `Sim_HFL` の `APSelectionDataset`（`sim/data_gen.py`）で **手続き的合成データ**を生成している。実機と同じ CSV パイプラインに切り替える場合は **クライアント側の読み込み変更**が別途必要。

**アプリ種別**（browser / video / call / other）は、環境変数 `APP_CATEGORY` 等で **論理クライアント側の属性**として実機に揃えやすいが、上記の観測・実装差は残る。

## 5. TP/RTT の「実数性」（よくある誤解の整理）

「Docker だと TP/RTT が実数ではなくなる」という理解は、**「その場の無線を端末が測った実数」**という意味では **正しい**。ただし **数値の出所**で次のように分けると正確。

| 出所 | 実数か | 備考 |
|------|--------|------|
| **実機・当該ラウンドの観測** | 実リンクに基づく（設計次第） | 主結果の主張と整合 |
| **配布 CSV に記録された過去の実測** | ファイル上は実測値 | **再生**であり、当該ラウンドのライブ測定ではない |
| **`APSelectionDataset` / `data_gen`** | モデル式・乱数由来 | **合成** |
| **`virtual_congestion` 等の API** | サーバ側モデルの出力 | **注入**であり、端末の RF 直接測定ではない |

デフォルトで合成データ＋仮想混雑 API に寄せると、**数値はどんどん「合成・モデル寄り」に見える**のはそのため。CSV を実測ログにすれば **学習特徴は実測由来に寄せられる**が、**ライブ実リンクの主張**は別途実機（またはトレース設計の明示）が必要。

---

## 6. いつ Docker を「使い出す」とよいか（方針メモ）

- **使い出す価値が大きい**: プロトコル安定化、サーバ負荷・同時接続、再現環境、論理クライアント数の感度分析（**主集約と切り分けて**記述）。
- **実機に置くべき主張**: 実リンク、実 AP 切替、端末上の学習再現性を論文の核にする部分。

**推奨の割り切り**: **実機少数を軸にし、Docker はサーバ再現＋補助クライアント**。「全部 Docker」に寄せると、これまで整理した **実数／合成の線引き**と論文表現が難しくなる。
