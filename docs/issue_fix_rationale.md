## 1. なぜこの整理が必要か

本研究は **実 Android 端末**、**Python サーバ（階層連合学習）**、**オフラインシミュレーション（Sim_HFL）** の三層が同時に存在します。それぞれが独立して「動いているように見えても」、次のような場合に **結論が無効** になります。

- クライアントとサーバーで **同じ名前の概念**（ラウンド、端末 ID、モデル形式）が **別物** を指している。
- メトリクスやログが **実験 run を区別できず**、別日の結果が混ざる。
- シミュレーションが **別の学習問題・別の物理モデル** を解いており、実機結果との比較が **意味をなさない**。

本稿では、フェーズごとに「何が危うかったか → 何を直したか」を因果でつなぎます。細目のファイル名はチェックリスト側に任せ、ここでは **説明と解釈** に重きを置きます。

## 2. Android とサーバーの「契約」がずれていたときのリスク

### 2.1 エンドポイントとメタデータ形式

**起こりうること**  
モデル配布用の URL やパス（例: `send_to_device`）が端末とサーバーで食い違うと、端末は **404 や古いキャッシュ** に落ち、**最新グローバルモデルで学習していない**まま FedAvg に参加する可能性があります。  
`format_version` が整数と文字列で混在すると、パーサや検証が **例外で止まる**か、**黙って誤解釈**するかのどちらかになり、再現性が崩れます。

**修正の意図**  
「どの URL で何を取るか」「メタ JSON の型は何か」を **単一の契約** に固定し、配布パイプライン全体で同じ前提にしました。

### 2.2 キー名の不一致（`session_id` と `run_id`）

**起こりうること**  
サーバーが `run_id` を必須とする一方、端末が別名で送っていると、**サーバー側で run が紐づかない**、または **常にデフォルト値** に落ちます。結果として、後段の分析 DB では「同じ実験」とみなせず、**論文用の集計が信頼できない**状態になります。

**修正の意図**  
フォームフィールド名をサーバー契約に合わせ、**実験セッションの識別子を一貫して伝播**させることにしました。

## 3. 実験の同一性と追跡可能性

### 3.1 `run_id` が無い世界

**起こりうること**  
`round_id` だけでは、「月曜の round 5」と「金曜の round 5」を区別できません。複数端末・複数エッジでは、**ログの突合**や **バグ再現**が極めて難しくなります。

**修正の意図**  
実験開始時に UUID 形式の `run_id` を生成し、端末・サーバー・（可能なら）ログ行に載せることで、**1 本の実験を時系列で追える**ようにしました。

### 3.2 `terminal_id` の混在

**起こりうること**  
デバイス名とパッケージ名など、**別の名前空間**が `terminal_id` として混ざると、エッジの許可リスト・重みファイルの衝突・ダッシュボード表示が **一貫しません**。連合学習では「誰の更新か」が集約の前提なので、ここが曖昧だと **重みの帰属誤り** に直結します。

**修正の意図**  
識別子の意味を **`device_id` に統一**し、サーバーと端末で同じ解釈にしました。

### 3.3 メトリクス送信で `null` が続く問題

**起こりうること**  
`run_id` やサイクル番号、バッテリなどが `null` のまま DB に入ると、**後から「そのラウンドで何が起きたか」を説明できない**うえ、論文用の図表を作る段階で **欠損だらけ** になります。

**修正の意図**  
送信直前までに **実際の状態をすべて埋めてから** アップロードするよう、ViewModel 側の責務を明確にしました。

### 3.4 メトリクス削除が run 非対応だった問題

**起こりうること**  
新しい実験を始めるときに、**過去の全実験のメトリクスが消える**と、比較実験や追試ができません。

**修正の意図**  
削除単位を **`run_id` 単位**にし、実験のライフサイクルとデータのライフサイクルを一致させました。

## 4. 端末・サーバーの運用耐性

### 4.1 HTTP エラーがログに残らない

**起こりうること**  
現場では一時的な 5xx や認証エラーが起きます。端末側に **構造化ログが残らない**と、「学習が遅い」「同期しない」などの報告に対して **原因を特定できず**、研究スケジュールを圧迫します。

**修正の意図**  
`RealTimeLogger` にエラーコードと文脈を残し、**オフライン調査可能**にしました。

### 4.2 サーバーラウンド待ちの無限ブロック

**起こりうること**  
中央・エッジの不調やネット切断のとき、端末が **永久待ち**すると UI が固まり、実験セッション全体が回収不能になります。

**修正の意図**  
タイムアウトを設け、**失敗として検知・回復**できるようにしました。

### 4.3 エッジ集約コードのクラッシュ（存在しない属性参照）

**起こりうること**  
1 台でもアップロードがあるとエッジ集約が走る設計のもと、**属性参照ミスでプロセスが落ちる**と、**全端末のパイプラインが停止**します。連合学習実験では「1 箇所のバグが全クライアントに波及」しやすい典型例です。

**修正の意図**  
実際に存在するフィールド（例: `client_meta` 内の JSON）から指標を読むよう変更し、**集約の安定性**を優先しました。

## 5. シミュレーションが実機と違うと何が壊れるか

### 5.1 別の学習問題を解いている

**起こりうること**  
実機は **満足度ティア（4 クラス）** を予測する MLP なのに、シミュが **2 クラスの AP 選択**のままだと、**出力の意味・損失・精度の定義**が一致しません。「シミュで良かったから実機でも良い」という主張が **論理的に成立しません**。

**修正の意図**  
タスク定義・入出力次元を実機に合わせ、**同じ関数を近似している**という比較の前提を満たしました。

### 5.2 ハイパーパラメータと正則化の違い

**起こりうること**  
学習率・weight decay・バッチサイズが違えば、**収束速度・汎化・連合学習でのドリフト**まで変わります。LayerNorm にまで weight decay が掛かるなど、**オプティマイザの等価性**が崩れていると、「Kotlin と PyTorch で同じアルゴリズム」とは言えません。

**修正の意図**  
実機 Kotlin の設定に揃え、必要なら **スケジューラを手動実装**してまで学習ダイナミクスを近づけました。

### 5.3 データ分布と AP のコントラスト

**起こりうること**  
ラベルが一クラスに偏る、両 AP で常に満足度が最大、といった設定では、**AP 切替や方策の違いが学習信号として現れません**。その状態で「AP 選択の効果」を議論すると **偽陽性** です。

**修正の意図**  
ティア分布を意図的に整え、AP ごとに **QoS が分かれる**設定にし、**切替の動機がデータ上に存在する**ようにしました。

## 6. データ・学習過程・集約まわりの正しさ

### 6.1 データ分割と乱数の使い方

**起こりうること**  
実機が「先頭 N 件を逐次に使う」方式なのに、シミュだけ `random_split` だと、**非 IID の形が違う**ため、FedAvg の挙動比較が歪みます。

**修正の意図**  
分割手順を実機の考え方に寄せ、**同じ種類のデータ使用パターン**で比較できるようにしました。

### 6.2 集約バグ（NaN 除外とインデックス）

**起こりうること**  
無効な更新を除いたあと、**別のクライアントのメトリクスと ID が対応しなくなる**と、ログ上は「誰が参加したか」「平均精度はいくつか」が **誤表示**されます。論文用の JSONL をそのまま信じると **誤った結論** に直結します。

**修正の意図**  
有効なインデックスだけを明示的に管理し、**集約結果とメタデータの整合**を保証しました。

### 6.3 理論比較の誤変換・パラメータ数の誤算

**起こりうること**  
`accuracy = 1 - loss` のような **数学的に根拠のない変換**は、理論セクションや通信量見積もりを **誤った数値**で飾ることになります。パラメータ数を 58 のままにすると、**通信コストのオーダーが約 3 倍誤る**など、定量的主張が崩れます。

**修正の意図**  
比較可能な量だけを並べ、パラメータ数は **実アーキテクチャに基づき再計算**しました。

### 6.4 AP 選択ロジックとログ復元

**起こりうること**  
ラベル設計が変わったあとも、**旧ルール（予測アプリと正解アプリの比較）**が残っていると、シミュ上の「切替率」「満足度」が **別の現象**を指します。JSONL 復元で必須キーが欠けると、**再プロットや追加実験が再現できません**。

**修正の意図**  
ティア基準の方策に合わせ、ログスキーマも **欠落なく読める**ようにしました。

### 6.5 推論入力と「正解 AP」判定の TP/RTT の不一致

**起こりうること**  
モデルに入れた特徴と、`best_ap` の教師ラベル計算に使ったネットワーク条件が **別サンプル**だと、**教師ノイズ**が入り、学習が意図せず楽／難しく見えます。

**修正の意図**  
同一乱数系列で生成した TP/RTT を **入力・ラベル・満足度**で共有しました。

### 6.6 満足度の before / after

**起こりうること**  
実機は切替前後で満足度を分けて計測するのに、シミュが一値だけだと、**論文の図と実機の図が同じ意味を持たない**可能性があります。

**修正の意図**  
`before` / `after` を分離し、**報告項目の対応**を取りました。

## 7. 実機フローとシミュを揃える意味

### 7.1 集約タイミング

**起こりうること**  
実機は **各ローカルラウンドのたびに** エッジ→中央→再配布が回るのに、シミュが **30 グローバルラウンドの最後だけ**集約していると、**更新が伝播する速さ・データリークの有無**まで含めて別のアルゴリズムです。

**修正の意図**  
実機のサイクルに合わせ、**同じ階層 FedAvg の時系列**になるよう直しました。

### 7.2 毎回モデル初期化の罠

**起こりうること**  
「リアルタイム性」を毎ラウンド完全初期化で表現しようとすると、**学習が続かず精度が底辺**に張り付き、「連合学習が機能しない」ように見えます。それは **評価設計の問題**なのか **手法の問題**なのかが混線します。

**修正の意図**  
累積学習（モデル引き継ぎ）に戻し、**収束とリアルタイム性のトレードオフ**を別パラメータで扱えるようにしました。

### 7.3 ネットワーク条件の物理モデル

**起こりうること**  
サーバの `virtual_congestion` が **待ち行列に基づく**のに、シミュが **Gaussian だけ**だと、TP/RTT の相関・飽和の仕方が違い、**同じ入力次元でも別世界**を見ています。

**修正の意図**  
`network_model.py` でサーバ式と **同じ式**を実装し、**シミュのリンク品質がサーバ注入値と同じ家族**になるようにしました。

### 7.4 QoS 要件と AP 定数・正規化レンジ

**起こりうること**  
`ap_config.json` と needTP/needRTT が違えば **満足度の定義が実機と不一致**。`ROUTER_PARAMS` と初期 TP/RTT が違えば **混雑の初期条件が不一致**。正規化上限が狭いと **観測のクリッピング**で情報が落ち、モデルが **頭打ち**になります。

**修正の意図**  
定数を実機・サーバのソースオブトゥルースに揃え、正規化レンジを **実測しうるレンジ**まで広げました。

## 8. 環境・Docker 仮想端末

### 8.1 パスとスクリプト

**起こりうること**  
Windows 固有パスが残ると、**他メンバーや CI が即座に失敗**します。PowerShell のみだと **Mac/Linux 研究者が参加しにくい**です。

**修正の意図**  
パスを環境非依存にし、bash 版スクリプトを用意して **再現性とオンボーディング**を改善しました。

### 8.2 Docker 仮想端末のバイナリ送信

**起こりうること**  
f32_flat を JSON リストとして送ろうとすると、**ペイロードが巨大・非効率**であるうえ、サーバーが期待する **multipart バイナリ契約**を破ります。結果として **エッジが重みを解釈できず**、仮想端末実験全体が成立しません。

**修正の意図**  
`struct.pack` と multipart で **実機と同系の送信形式**に寄せました。

### 8.3 集約閾値（補足）

**起こりうること**  
中央・エッジの既定閾値が 1 のままだと、**複数エッジ・複数端末の階層 FedAvg**が「1 台分だけで進む」誤動作をし、**集約の意味が変質**します。

**緩和**  
`start.py` が子プロセスに閾値を注入し、`docker/docker-compose.yml` も **中央2・エッジ 2 と 1** に合わせています。`uvicorn` 単体起動時は従来どおり環境変数の明示が必要です（詳細は `RUN_GUIDE.md`）。

## 9. 残っている論点（概要）

チェックリスト（[`research_progress_issues.md`](research_progress_issues.md) フェーズ5）に列挙したとおり、**完全には閉じていない論点**があります。説明資料で触れるなら、次のように要約できます。

- **層名の不一致**（f32_flat と MLP のキー名）: 解析パスが分岐すると **デバッグコスト**が跳ねる。
- **legacy エンドポイント併存**: 誤った URL を叩くと **旧モデルで学習が続く**リスク。
- **切替クールダウン**: 実機にあってシミュにないと **切替頻度の比較**が公平でない。
- **ベースライン不足**: 提案手法の優位を **数値で証明する実験設計**がまだ弱い。
- **ラウンド数と収束**: 30 ラウンド前提の余裕が小さいと、**再現実験で失敗率**が上がる。

これらは「実装バグ」というより **実験デザインと API 整理**に近い課題が混ざっています。
