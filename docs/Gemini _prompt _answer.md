  シミュレーションと実機（Android）間における設計不一致の調査結果と回答

  回答日: 2026-04-27
  調査対象: Sim_HFL (Python) および HFL_terminals (Android)
  結論: 「対象APスコア（AP ID直接予測）」 方式が本来の設計意図であり、正解です。

  ---

  1. 調査結果の要約

  リポジトリ内のソースコード（先行研究のコアロジック）を徹底調査した結果、AIモデルの出力は 「次に接続すべき最適なAPのインデックス（AP ID）」
  を予測するように設計・学習されていることが確認されました。

  prompt.md で懸念されていた「満足度ティア予測」方式は、現行の学習データ生成ロジックおよびシミュレーション実行コードの実装と矛盾しています。

  ---

  2. 根拠となるエビデンス

  ① 教師データの内容 (hungarian_main.py)
  学習データのラベル生成部分を確認したところ、正解データ（y）には「満足度」ではなく、ハンガリアン法によって算出された 「最適なAPのID」 が格納されています。

   1 # hungarian_main.py より抜粋
   2 ap_id = int(combination.combiApTermArray[term.id]) # 最適なAPのIDを抽出
   3 csv_writer.writerow([app.needTP, app.needRTT, term.appNum, ap_id]) # ラベルとして保存

  ② 推論結果の利用箇所 (HFL_main.py)
  シミュレーション内での推論結果（pred_labels）は、そのままAPの切り替え関数（setSwitchAp）の引数として利用されています。

   1 # HFL_main.py より抜粋
   2 for item in range(len(TERMS)):
   3     TERMS[item].setSwitchAp(list_apNum[item]) # 出力インデックスをAP IDとして扱う

  ③ 既存ドキュメントの記述 (HFL_Simulation_Report.md)
  「学習パイプラインは [needTP, needRTT, appNum, target_ap_id] の入力を前提とする」と明記されており、出力が target_ap_id であることが定義されています。

  ---

  3. 各環境における解釈の修正案

  調査結果に基づき、以下の通り設計を統一することを推奨します。

  ┌────────────────┬───────────────────────────────────┬───────────────────────────────────┐
  │ 項目           │ Android実機側 (DecisionEngine.kt) │ シミュレーション側 (terminal.py)  │
  ├────────────────┼───────────────────────────────────┼───────────────────────────────────┤
  │ 設計の現状     │ 正しい（AP ID方式）               │ 誤解（ティア方式）                │
  │ 出力の解釈     │ argmax の結果を接続先APとする     │ 修正が必要：ティア判定を廃止する  │
  │ 入力データ     │ アプリの要求品質 (TP/RTT)         │ アプリの要求品質 (TP/RTT)         │
  │ 修正アクション │ そのまま維持                      │ 推論ロジックを「AP ID選択」へ戻す │
  └────────────────┴───────────────────────────────────┴───────────────────────────────────┘

  ---

  4. 結論と推奨アクション

  Android実機側の DecisionEngine.kt
  のロジック（最もスコアが高いAPを選ぶ）は、先行研究の設計意図および学習データの構造と完全に一致しています。実機側のロジックを「満足度ティア判定」に改修する必要はありません。

  逆に、シミュレーション側の解釈が「満足度ティア」になっている場合、以下の問題が発生します。
   - モデルの意図を誤解: モデルが「AP 0番が最適だ」と答えているのに、シミュレーション側が「不満（ティア0）だ」と誤解してしまいます。
   - 致命的なバグの誘発: prompt.md で指摘された通り、通信が悪いときにそのAPに固執する挙動になります。

  今後の作業指針:
   1. シミュレーション側のコード修正: 満足度に基づく切り替え判定（Tier 0/1なら切り替える等）を行っている箇所があれば削除し、モデルの出力をそのまま接続先AP IDとして扱うように修正してください。
   2. 入力データの統一: 入力が「現在の品質」ではなく「アプリが必要とする品質（要求条件）」になっていることを再確認してください。

  この修正により、シミュレーションで得られた学習成果（.pt モデル）をそのまま実機にデプロイし、意図した通りのAP切り替え動作を実現することが可能になります。
