# サーバ要件チェックリスト

以下は、中央サーバ側から提示された要件に基づいて、端末側で実装およびテストが必要な項目のチェックリストです。

## 要件

1. **エンドポイントの実装**
   - [ ] POST `/api/training-data` が正しく実装されている。
   - [ ] コンテンツタイプが `application/json` である。
   - [ ] JSON スキーマが `TRAINING_DATA_API.md` に記載された仕様に準拠している。

2. **レスポンスの確認**
   - [ ] 成功時に HTTP 200 と `{ "status": "ok", "id": <保存ID> }` が返される。
   - [ ] バリデーションエラー時に HTTP 400 が返され、レスポンスにエラー詳細が含まれる。
   - [ ] サーバ内部エラー時に HTTP 500 が返される。

3. **テスト送信**
   - [ ] テスト送信を実施し、HTTP 200 が返ることを確認する。
   - [ ] 中央の DB にレコードが正しく保存されていることを確認する。
   - [ ] 型ミスなどの検証エラーがある場合、HTTP 400 が返ることを確認する。

4. **ログの共有**
   - [ ] 送信結果（端末ログ）を取得し、中央サーバのログ（`training_data_received` イベント）と照合する。

5. **重複送信の防止（新規追加）**
   - [ ] 同一ラウンドで複数回送信された場合、最初のデータのみを採用する `first-wins` ポリシーを実装する。
   - [ ] `(terminal_id, round_id)` をキーとして永続的に記録し、重複データを無視する。
   - [ ] 重複データを無視した場合、レスポンスとして `{ "status": "duplicate_ignored" }` を返す。

## 注意事項
- バリデーションレスポンスを HTTP 400 から 422 に変更する要望がある場合、サーバ側に連絡してください。
- 必要に応じて、DB の移行や可視化テンプレートの提供を依頼してください。

## 実施状況

# 端末（クライアント）向け要求書 — サーバ（中央/エッジ）との送信ルール

## 目的
端末が生成したローカル集約（または端末が持つ重み）を安全かつ重複なくサーバに届けるための実装ルール。
既存サーバは「first-wins（edge+round ごとに最初に受け入れた更新を採用）」の運用になっています。端末側はこれに従って送信/再送を行ってください。

---

## 1) 要点（短く）
- 端末は以下のフィールドを必ず送信すること:
  - `edge_id`, `round`, `num_clients`, `sum_n_samples`, `weights`（ファイル）
- コンテンツは1回のみ送る（first-wins方針）。通常は ACK を受けたら再送しない。
- ネットワーク障害時は限定的に再送する（下の再送ポリシー参照）。
- サーバは同じ `edge_id` + `round` の2回目以降を無視（`duplicate_ignored`）。
- サーバが返す応答を見て送信結果を永続化（成功マーク）すること。ACKが無ければ限定回数の再試行を行う。

---

## 2) 送信先 & リクエスト形式
- **HTTP メソッド**: POST
- **Content-Type**: multipart/form-data
- **送信先エンドポイント**: `/edge_update`

### フォームフィールド（必須/推奨）
| フィールド名         | 必須/任意 | 説明 |
|----------------------|-----------|------|
| `edge_id`           | 必須      | 重みを送る端末が所属するエッジの識別子（文字列） |
| `round`             | 必須      | 現在のラウンド番号（整数） |
| `num_clients`       | 必須      | エッジが集約した端末数（整数） |
| `sum_n_samples`     | 必須      | 合計サンプル数（整数） |
| `weights`           | 必須      | アップロードする重みファイル（例: `.pt` ファイル） |
| `model_id`          | 任意      | 実験/ジョブの識別子（文字列） |
| `base_hash`         | 任意      | 基本ハッシュ値（文字列） |
| `event_timestamp`   | 任意      | イベント発生時刻（フォーマット: `YYYYmmdd_HHMMSS_ffffff`） |
| `content_sha256`    | 任意      | アップロードするバイナリの SHA256 ハッシュ（形式: `sha256:<hex>`） |

---

## 3) タイムスタンプとタイムゾーン
- `event_timestamp` は端末ローカル時間で OK。ただしフォーマットは厳守（`YYYYmmdd_HHMMSS_ffffff`）。
- サーバは受信時に `ack_timestamp` を付与して返します（フォーマット: `YYYYmmdd_HHMMSS_ffffff`）。
- 端末はこの `ack_timestamp` を保存しておくと監査に便利です。

---

## 4) 応答の読み方（サーバが返す代表的な JSON）
- **成功（集約を待っている場合）**
  ```json
  {
    "status": "accepted_and_waiting",
    "message": "...",
    "collected_edges": N,
    "aggregation_threshold": T
  }
  ```
  意味: 受領され、しきい値に達していない。送信は成功とみなして良い（再送不要）。永続化しておくこと。

- **成功（集約をキューに入れた場合）**
  ```json
  {
    "status": "accepted_and_queued",
    "message": "...",
    "collected_edges": N,
    "aggregation_threshold": T
  }
  ```
  意味: 受領され、しきい値に達したため集約タスクをキューに入れた。成功扱い。

- **重複（同一 edge + round で既に受け入れ済み）**
  ```json
  {
    "status": "duplicate_ignored",
    "ack": true,
    "ack_timestamp": "...",
    "sha256": "sha256:..."
  }
  ```
  意味: サーバ側で重複と判断。再送しないで良い（成功扱い）。

- **エラー例**
  - `422 hash_mismatch`: `content_sha256` と実データ不一致 → 再送しない（原因を調査）
  - `400 empty_payload`: ペイロード不正 → ログを確認、再送は行わない
  - `500 aggregation_or_save_failed`: サーバ側で集約/保存に失敗 → 一時的な問題の可能性。リトライポリシーに従う

---

## 5) 再送ポリシー（推奨）
- **最大再送回数**: 5
- **初回バックオフ**: 2 秒（指数バックオフ: `2^attempt` 秒、最大バックオフ: 60 秒）
- **再送条件**:
  - ネットワークエラー、接続タイムアウト、HTTP 5xx
- **再送しない条件**:
  - `422 hash_mismatch`、`400` 系その他の明確なクライアント側エラー

---

## 6) テストケース（端末側で実行すること）
- **正常ケース**: 単一のペイロードを送信し、サーバが `accepted_and_waiting` または `accepted_and_queued` を返すことを確認。
- **重複送信ケース**: 同じペイロードを連続で送信し、2回目が `duplicate_ignored` を返すことを確認。
- **ネットワーク切断リトライケース**: タイムアウト時に再送が行われ、最終的に成功または上限到達で停止することを確認。
- **ハッシュ不一致ケース**: 故意に間違った `content_sha256` を送信し、`422 hash_mismatch` が返ることを確認。

---

## 端末側の変更点

1. **送信データの形式統一**:
   - `edge_id`, `round`, `num_clients`, `sum_n_samples`, `weights`（ファイル）を必須フィールドとして送信する。
   - 任意フィールドとして `model_id`, `base_hash`, `event_timestamp`, `content_sha256` を追加可能。

2. **SHA256 ハッシュの計算と送信**:
   - アップロードする重みファイルの SHA256 ハッシュを計算し、`content_sha256` フィールドに含める。
   - ハッシュ計算例（Python）:
     ```python
     import hashlib
     content_bytes = open("weights.pt", "rb").read()
     content_sha256 = "sha256:" + hashlib.sha256(content_bytes).hexdigest()
     ```

3. **再送ポリシーの実装**:
   - 最大再送回数を 5 回に設定。
   - 初回バックオフを 2 秒とし、指数バックオフ（`2^attempt` 秒）を採用。
   - 再送条件:
     - ネットワークエラー、接続タイムアウト、HTTP 5xx。
   - 再送しない条件:
     - `422 hash_mismatch`、`400` 系その他のクライアントエラー。

4. **ローカル永続化**:
   - `(run_id, round)` をキーとした送信台帳を作成し、送信状況を永続化。
   - 成功時に ACK タイムスタンプを保存。

5. **テストケースの実施**:
   - 正常ケース、重複送信、ネットワーク切断時のリトライ、ハッシュ不一致時の挙動を確認するテストを実施。

---

## サーバ側に要求すること

1. **エンドポイントの安定性向上**:
   - 高負荷時のレスポンス遅延を最小化するため、非同期処理の最適化を検討。
   - 再送ポリシーに基づくリクエストを正確に処理するため、タイムアウトやリトライに関するログを詳細に記録。

2. **レスポンスの一貫性**:
   - 成功時、重複時、エラー時のレスポンス形式を統一。
   - 例: `status`, `message`, `ack_timestamp` を含む JSON を返す。

3. **ハッシュ不一致時の詳細情報提供**:
   - `422 hash_mismatch` エラー時に、期待されるハッシュ値をレスポンスに含める。
   - 例:
     ```json
     {
       "status": "error",
       "code": "hash_mismatch",
       "expected": "sha256:...",
       "received": "sha256:..."
     }
     ```

4. **メタデータの取得エンドポイント**:
   - 現在のラウンドやモデル情報を取得するためのエンドポイントを提供。
   - 例: `/api/v1/meta` で `round`, `model_id`, `base_hash` を返す。

5. **監査ログの共有**:
   - 端末からのリクエストに対するサーバ側の処理状況を確認できるよう、監査ログを定期的に共有。

6. **テスト環境の提供**:
   - 端末側でのテストを容易にするため、ステージング環境やモックサーバを提供。
