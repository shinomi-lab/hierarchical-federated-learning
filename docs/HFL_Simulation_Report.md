# HFL AP Selection Simulation: アーキテクチャおよび実装・解析レポート

## 1. プロジェクト概要と目的
本プロジェクトは、モバイルネットワーク環境において、各端末（Terminal）が要求するスループット（TP）や遅延（RTT）を満たす最適な基地局（Access Point: AP）を予測・選択するためのシミュレーションシステムです。
最適化の正解データ（ハンガリアン法などで生成された割り当て）をもとに、階層型フェデレーテッドラーニング（HFL: Hierarchical Federated Learning）を用いてモデルを学習させ、その学習済みモデルを用いてリアルタイムなAP選択シミュレーションと性能評価（満足度の計算）を行います。

---

## 2. システムアーキテクチャと実行フロー

システムは主に「①データ生成」「②HFLモデル学習」「③シミュレーション実行・評価」の3つのフェーズで構成されています。

### ① 教師データ生成フェーズ (`hungarian_main.py`)
エージェントが学習するための「正解ラベル」を持ったデータセットを生成します。
- **入力:** 端末数、AP数、初期RTT、Erlang-Bモデルにおける回線数(`erlang_n`)などのパラメータ（対話式または `sim.json` から取得）。
- **処理フロー:**
  1. 端末 (`Term`) と基地局 (`Ap`) のインスタンスをランダムな初期状態で生成。
  2. 各端末に利用するアプリケーション（`app.json`で定義）をランダムに割り当て。
  3. ハンガリアン法 (`hung.call_hungarian`) を用いて、システム全体の要件（TP/RTT）を満たす最適なAP割り当てを算出。
  4. 割り当て結果に基づき、各端末の「必要TP」「必要RTT」「アプリID」「最適APのID（ラベル）」をCSV形式（例: `70_event.csv`）に出力します。

### ② HFL（階層型フェデレーテッドラーニング）学習フェーズ (`HFL_main.py`, `create_hierarchy.py`, `update.py`)
生成されたCSVデータを読み込み、分散環境を模した階層構造でニューラルネットワークモデルを学習します。
- **データローディング:** `DatasetSplit` を用いて、CSVから読み込んだデータを各クライアント（ユーザ）に分割して割り当てます。
- **階層構造の構築 (`create_hierarchy.py`):**
  - **Terminal (User):** 実際のデータを持つ末端。ローカルでモデルを学習（`LocalUpdate` in `update.py`）。
  - **Edge Server:** 複数のTerminalを束ねる中間サーバー。ローカルモデルの重みを集約します。
  - **Central Server:** 全Edge Serverから重みを集約し、グローバルモデルを更新します。
- **モデル (`models.py` / 推測):** CNNまたはMLP（多層パーセプトロン）。入力は端末の要求スペック（TP, RTT, アプリ種別のOne-Hotエンコーディング）、出力は各APを選択すべき確率（クラス分類問題）として扱われます。

### ③ シミュレーション実行・評価フェーズ (`HFL_main.py`)
学習済みのHFLモデルを利用して、時間経過に伴う動的な環境下でのAP選択シミュレーションを実施します。
- **反復処理:** 指定された時間ステップ（Time steps）にわたってシミュレーションを回します。
- **推論 (`test_inference` in `update.py`):** 各ステップで、端末の現在の要求（TP/RTT）をモデルに入力し、予測される最適なAPへ接続を切り替えます。
- **パフォーマンス評価:** 切り替え後のシステム全体のパフォーマンス（端末満足度など）を計算し、グラフ等で可視化します。

## 3. 主要なデータ構造 (Entities)

シミュレーションを構成する主要なクラス・構造は以下の通りです。

### 基地局 (Access Point): `ap.py`
- `bssid` (str): 基地局の識別子。
- `rtt` (float): 現在のラウンドトリップタイム（遅延）。
- `tp` (float): 現在のスループット。
- `termNum` (int): 接続されている端末数。
- 接続端末数が増減するたびに、`cal.py` のロジックによって `rtt` と `tp` が動的に再計算されます。

### 端末 (Terminal): `term.py`
- `id` (int): 端末識別子。
- `apBssid` (int/str): 現在接続しているAPのID。
- `appNum` (int): 現在使用しているアプリケーションのID。
- `lines` (list): 転送データ量などの通信制限・履歴を管理するオブジェクト。

### アプリケーション要件: `app.json` / `termApp` (`cal.py`)
- アプリケーションごとに `indicator` (最適化の主指標: `tp` または `rtt`) と、それぞれに必要な閾値 (`needTP`, `needRTT`) が定義されています。

## 4. コアロジックと分析アルゴリズム (`cal.py`)

エージェントが結果を評価・分析するための核となる数学的計算が実装されています。

### 通信品質（Link Quality）の計算 (`calLink` 関数)
各APに接続された端末数(`termNum`)に基づき、動的な通信品質を算出します。
- **スループット (TP):** **Erlang-B式** (`erlang_b`) を使用し、呼損率（ブロック率）を計算。これに基づき、初期TPから実際の利用可能TPを減衰させます。
- **遅延 (RTT):** **M/M/1待ち行列モデル** (`response_time_mm1`) を使用し、トラフィック量に応じた応答時間を計算し、RTTを導出します。

### 端末満足度の計算 (`calSatis`, `calSatisTerm` 関数)
モデルの予測がどれだけ優れているかを測るための主要な評価指標（Reward/Metric）です。
- **個別満足度:** 
  - `indicator == 'tp'` の場合： `APの現在のTP / 端末の必要TP`
  - `indicator == 'rtt'` の場合： `端末の必要RTT / APの現在のRTT`
- **システム全体の満足度:** 
  - 単純な平均ではなく、極端に不満を持つ端末をシステム全体で重く評価するため、全端末の満足度の **「調和平均 (Harmonic Mean)」** を計算しています（逆数を足し合わせてから割る手法）。

### ギャップの計算 (`calGap`, `calGapTerm` 関数)
要求されているスペックと、実際のAPの提供スペックの「絶対的な差（乖離）」を計算します。RTTが指標の場合は、計算のためにRTTからTP相当の要求値に変換して比較する工夫がなされています。

## 5. 次期プロジェクトの実装エージェントへ向けたインサイト

このコードベースを参考に新たな実装や拡張を行うAIエージェントは、以下の点に留意してください。

1. **強化学習や別アルゴリズムへの転用:**
   - 環境からの「報酬（Reward）」関数を設計する際、`cal.py` の `calSatis`（調和平均による満足度）と `calGap` はそのままRewardの計算ロジックとして流用可能です。
   - 状態（State）は端末の要求（`needTP`, `needRTT`, `appNum`）、行動（Action）は対象のAP IDとなります。
2. **トラフィック理論の実装:**
   - 通信環境のシミュレーションにおいて、端末数に比例して線形に性能を落とすのではなく、M/M/1やアーランB式を適用する `calLink` の実装は、より現実に近いネットワークシミュレーションを構築する上で非常に価値があります。
3. **データフォーマットの互換性:**
   - 学習パイプラインはCSV形式（`[needTP, needRTT, appNum, target_ap_id]`）の入力を前提としています。別プロジェクトでデータを生成・加工する場合も、この配列順序とOne-Hot化のロジック（PyTorchのTensor変換時）を維持する必要があります。
4. **設定ファイルの分離:**
   - `sim.json`, `app.json`, `ap.json` にシミュレーションのハイパーパラメータやネットワーク構成が切り出されています。環境のスケールアップ（AP数や端末数の増加）を行う場合は、これらのJSONファイルおよび `erlang_mu`、`_DEFAULT_RTT` などのデフォルト配列長を動的に拡張するハンドリングに注意してください。
