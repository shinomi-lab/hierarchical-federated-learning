# 調査報告：推論スナップショット画面における端末・アプリ情報の不一致

## 1. 現象
サーバーの起動画面で `Tab` キー（または `Ctrl+I`）を押下した際に表示される「AP切り替え推論スナップショット」において、以下の不一致が発生している。
- **端末ID:** 実機で設定した名前ではなく、パッケージ名（`com.example...`）が表示される、または別の端末と情報が混ざる。
- **アプリ名:** 実機で実行しているアプリと異なる名前が表示される、あるいは Fallback（デフォルト値）が表示される。

## 2. 原因の分析

### A. 端末識別子（ID）の不整合
実機側の `TelemetrySender.kt` において、識別子の扱いが二重になっている。
- **JSONの中身:** `terminal_id` として設定済みの端末名を入れている。
- **通信パス（URL）:** `terminal_id` としてパッケージ名（`context.packageName`）を使用している。
- **サーバー側の挙動:** エッジサーバーおよび中央サーバーは、URLパスに含まれる ID を優先してディレクトリ作成やログ出力のキーとして使用しているため、表示がパッケージ名に引っ張られている。

### B. サーバー側表示ロジックの脆弱性（`start.py`）
推論画面の表示データ生成ロジック（`_do_inference_snapshot`）に以下の問題がある。
- **ログへの依存:** データベース（SQLite）ではなく、`logs/time_records/central_server_*.log` を直接パースして最新の1行を取得している。
- **辞書の上書き:** ログをパースして辞書（`terminal_data[tid]`）に格納しているため、複数の端末が同じパッケージ名（ID）でログを出すと、後のデータで情報が上書きされ、端末とアプリの組み合わせが崩れる。

### C. アプリ情報（`app_type`）の伝播不足
- **実機側:** `TelemetrySender` が送る JSON のトップレベルに `app_type` が含まれておらず、`training_metrics_last` というネストされたオブジェクトの中に隠れている。
- **サーバー側:** ログ出力時にトップレベルの `app_type` が空だと、推論画面では `app.json` の定義順に基づいた「Fallback表示」を行ってしまう。

## 3. 修正案（開発者向け）

### 案1：実機側の識別子統一（即効性あり）
`HFL_terminals` の `TelemetrySender.kt` において、送信時の `terminalId` 変数をパッケージ名ではなく、設定済みの端末IDを使用するように変更する。
```kotlin
// 修正前
val terminalId = context.packageName
// 修正後
val terminalId = AppConfig.getTerminalId(context)
```

### 案2：アプリ名のトップレベル化
実機の `TelemetrySender` からのテレメトリ送信時に、`app_type` を JSON のトップレベルに明示的に含める。

### 案3：サーバー表示ロジックの DB 参照化
`start.py` の `_do_inference_snapshot` を修正し、ログファイルのパースではなく `training_metrics.db` の `metrics` テーブルから最新レコードを取得するように変更する。これにより、揮発性の高いログパースによる誤表示を防ぐ。

---
**付記:**
この問題は、複数の実機を同時に動かしたり、同じ実機でアプリを切り替えて実験を繰り返したりした際に、古いログが残っていると特に顕著に発生します。
